# 《中小型企业智能财务报销系统》毕业设计说明书

## 1. 课题背景与意义
传统中小企业报销流程依赖纸质单据和手工核对，存在录入效率低、发票真伪难判断、报销单格式不统一的问题。本系统将发票验真、OCR识别、表单自动回填和标准报销单输出整合为单一链路，降低人工重复输入，提升报销准确性和规范性。

## 2. 需求分析
### 2.1 角色需求
系统仅设置一个角色：员工。员工可完成注册登录、发票上传、验真、OCR识别、报销单填写、草稿保存、提交报销、历史查询、首页统计。

### 2.2 功能需求
1. 登录注册：工号+密码登录，支持员工注册。
2. 发票上传与验真：上传发票文件，调用百度验真API。
3. 6位编码生成：仅在验真通过时生成编码，规则为年份后两位+4位流水号。
4. OCR识别回填：输入编码触发OCR，将识别结果回填。
5. 报销单生成：填写必要字段并生成通用标准报销单。
6. 打印与导出：支持print-js打印与jsPDF导出。
7. 草稿与提交：草稿暂存，提交后状态更新为已提交。
8. 历史与统计：查询个人报销记录，展示报销数量、验真成功数、报销总金额。

### 2.3 非功能需求
1. 可维护性：前后端分离，接口清晰。
2. 可扩展性：后续可增加审批角色和流程。
3. 可用性：页面简洁、操作路径短。
4. 安全性：密码哈希存储，发票验真失败严格阻断后续流程。

## 3. 可行性分析
### 3.1 技术可行性
Vue3 + Element Plus可快速搭建交互界面；Django + DRF适合中小规模REST接口开发；MySQL可满足结构化数据持久化；百度智能云API提供标准化发票验真/OCR能力。

### 3.2 经济可行性
系统依赖开源技术栈，部署成本低；百度API按调用计费，适合课设与小规模试运行。

### 3.3 运行可行性
浏览器即可访问，后端部署在普通Windows/Linux环境可运行，便于实习与毕业设计并行交付。

## 4. 系统总体设计
### 4.1 架构设计
采用前后端分离架构：
- 前端：Vue3 + Element Plus + Axios + print-js + jsPDF
- 后端：Django4.x + DRF
- 数据库：MySQL8.0
- 第三方：百度增值税发票验真与OCR API

### 4.2 模块设计
1. 用户模块：注册、登录、会话保持（本地存储）。
2. 发票模块：上传、验真、编码生成、OCR识别。
3. 报销模块：表单填写、金额大写转换、草稿/提交。
4. 历史模块：按状态查询、记录展示。
5. 统计模块：首页关键指标汇总。

## 5. 数据库设计
核心三表：employee、invoice、reimbursement。
- employee与invoice为1对多。
- employee与reimbursement为1对多。
- invoice与reimbursement为1对1，确保单发票不重复报销。

详细建表语句见 sql/smart_reimbursement.sql。

## 6. 核心业务流程设计
1. 员工登录系统。
2. 上传发票并提交验真字段。
3. 后端调用百度验真接口。
4. 验真失败：流程终止，不生成编码。
5. 验真成功：生成6位编码并保存。
6. 员工输入6位编码执行OCR。
7. 后端解析OCR结果并自动回填。
8. 员工补充报销信息，生成标准报销单。
9. 支持打印和PDF导出。
10. 草稿保存或提交报销。
11. 在历史页面与首页统计中查看结果。

## 7. 关键算法说明
### 7.1 6位编码生成算法
- 前2位：当前年份后两位，例如2026年为26。
- 后4位：同年度递增序号，不足4位左补零。
- 示例：260001、260002。
- 采用数据库行级锁避免并发重复。

### 7.2 发票金额大写转换
将金额保留两位小数后，转换为中文金额大写，支持元角分输出，生成报销单标准字段。

## 8. 系统测试方案
### 8.1 功能测试点
1. 注册/登录正确性测试。
2. 验真失败阻断测试。
3. 验真成功编码唯一性测试。
4. OCR回填正确性测试。
5. 报销草稿与提交状态测试。
6. 同一发票重复提交拦截测试。
7. 打印与导出功能可用性测试。

### 8.2 性能与稳定性测试
- 单用户并发场景下接口响应稳定。
- 上传大文件时有类型和逻辑校验。

## 9. 结论与展望
本系统实现了从发票验真到报销提交的完整闭环，满足本科毕业设计“功能完整、技术适中、可演示可交付”的要求。后续可扩展审批流、多角色权限、报销预算控制、统计图表与消息提醒等能力。
